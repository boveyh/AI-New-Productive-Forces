### 1.2 有意不做

- **不新增章节**：导航仍是 8 章，总结挂在结论章内部。
- **不引入图表库**：继续手写 SVG，维持零新增运行时依赖。

## 2. 设计要点

### 2.1 尺寸预算（把"过大"换成可验收的数字）

先立预算，再改布局，否则改完仍无法判定合格。

以桌面 1440×900 视口（实测可用高度 804px）为基准：

| 指标 | 上限 | 现值（阈值 / 响应面） |
| --- | --- | --- |
| 画布（SVG）高度 | ≤ 一屏 55%（≈440px） | 740 / 790 ❌ |
| 图表总高度 | ≤ 一屏 80%（≈640px） | 1125 / 1079 ❌ |
| 图表总宽度 | ≤ 容器宽（不溢出） | 通过 |
| **侧栏总高度** | **≤ 画布高度** | 新增约束 |

达成手段，四项叠加使用：

1. **双栏化**（≥1050px 启用）：左侧画布，右侧侧栏。把纵向堆叠改为横向并排——桌面横向空间是富余的，纵向才是稀缺的。画布拿到约 60% 宽度（≈740px）后，高度自然落到约 480px。
2. **画布 `max-width` 收紧**：即使双栏，也给画布一个硬上限（阈值 ≈ 660px、响应面 ≈ 640px），保证超宽屏不会再次放大。
3. **viewBox 纵横比微调**：阈值 460×300 → 460×270，响应面 460×320 → 460×280。仅压缩上下留白，不动数据映射逻辑（前提见任务 0.1）。
4. **侧栏内容按优先级裁剪**（见下表），保证侧栏不成为第二个纵向堆叠。

三者叠加后预期：阈值画布 ≈ 425px、总高 ≈ 640px；响应面画布 ≈ 435px、总高 ≈ 655px，均落回预算内。

1050px 以下退回单栏（现有行为），375px 需重新复测无横向溢出。

#### 侧栏内容清单（补强 1）

**侧栏存在的唯一理由是把纵向堆叠改成横向并排。** 若侧栏内容在右侧继续纵向堆叠、高度超过画布，双栏就白做了。因此立一条硬约束：

> **侧栏总高 ≤ 画布高。** 这是验收项，不是原则。

在此约束下，两图侧栏各自只放两类内容，按优先级取前 2 项；若仍超高，第 2 项折叠为一行、悬停展开：

| 图 | 侧栏内容（优先级从高到低） | 明确排除 |
| --- | --- | --- |
| 阈值图 | ① 图例（漏喷率 / 误喷率）② 读图要点 | **分段控件不进侧栏**——它是控制项，与"读数"分离会割裂操作与反馈；保留在画布下方 |
| 响应面 | ① 读数面板（投入 / 协同 / 指数 / gain / friction / 状态）② 点击后果说明 | **不重复放分段控件**——实验室四个滑杆已经承担该角色 |

两条推论：

- 阈值图的 `分段控件` 从当前"画布上方"移到**画布下方**，与画布同栏。这样侧栏只剩图例 + 要点，高度可控；
- 响应面的侧栏读数面板是有下界的（§2.2 至少要 6 行读数 + 1 行后果说明 + 1 行回退提示）。若 1050–1200px 区间超预算，优先折叠"点击后果说明"为常驻单行（**不得**折叠掉该行本身，因为它必须在点击前可见，见 §2.2 规矩 1）。

### 2.2 响应面交互模型

响应面天然适合直接操作，因为它就是实验室四个滑杆的二维切片。设计成两层：

**第一层：悬停 = 只读预览**
- 画布出现十字准星，跟随指针；
- 侧栏读数面板显示该点的 `投入 X% / 协同 Y% / 有效生产力指数 Z / 状态（人机协同 / 自动化陷阱 / 技术孤岛 / 尚未形成规模效应）`；
- 状态与文案直接取自 `evaluateProductivity` 的返回值，不另写一套判断，避免与滑杆区结论不一致；
- **同时显示 `gain` 与 `friction` 两个分量**——这是 §2.3 选 A 的前提：两个阈值哪个重要，由读者看这两个数自己判断，而不是由图注代答。

**第二层：点击 = 写入模拟器（允许，但必须可解释、可回退、可见）**

点击把 `investment ← x`，并把 `data / process / training` **三者统一设为 C**。这是刻意设计而非副作用：它直观解释了"协同基础是三者的几何平均"，正是纵轴的定义（见 `sampleSurface` 的注释）。但"一次动三个滑杆"必须被解释，否则用户会以为自己误操作，进而不敢再点。因此加三条规矩：

| 规矩 | 内容 | 为什么 |
| --- | --- | --- |
| **1 事前后果说明** | 侧栏**常驻**一行：「点击 = 把 data / process / training 统一设为该点的协同基础值」。点击**之前**就可见 | 点击后才解释等于事后补救；常驻才不会在用户犹豫时缺席 |
| **2 可见回退** | 点击后，读数区下方出现一行「已写入模拟器 · 点此恢复到点击前」，**保留到下一次任何输入变化为止** | 预设栏虽能一键回退，但用户点击后未必立刻想到去点预设栏。这不是新增状态管理：只记录一次 `previousInputs`，与预设按钮**共用同一条恢复路径** |
| **3 区分预览点与写入点** | 悬停的十字准星是**预览点**（空心）；点击后留下**写入点**（实心）。两者视觉明确不同 | 让用户一眼看出"我现在看的是哪"与"我实际设的是哪"，避免把预览误当已生效 |

**键盘可达**：画布 `tabIndex={0}`，方向键按 0.05 步进，`Home` / `End` 归零 / 拉满，配合 `aria-live` 文本读数。键盘移动即"预览点"移动；`Enter` / `Space` 触发写入（与点击同路径，同样遵守规矩 1–3）。

> **关于 `tabIndex`**：项目此前有一条"全站不得覆写 `tabIndex`"的验收项，用于防止键盘可达性退化。这里需要**唯一一处刻意的例外**，因为画布本身就是一个输入控件，不可聚焦就无法键盘操作。计划明确记录此例外，并在验收时用 `grep -rn "tabIndex" src/` 确认全站仍然只有这一处。

**性能**：不重算响应面。`sampleSurface` 的 `useMemo` 保持不变；悬停只在指针位置调用一次 `evaluateProductivity`（纯函数，成本可忽略）。

### 2.3 响应面参考线精度（必须先修，定案 A）

在动手做交互之前，先修一个已存在的问题。实测数值：

```
评价函数：index = 100 × (1 + 0.45·gain − 0.30·friction)
              gain = I·C,  friction = I·(1−C)
∂index/∂I = 100 × (0.75C − 0.3)  →  拐点在 C = 0.40
gain ≥ friction  ⟺  C ≥ 0.50
```

| C | I=0 | I=1 | 指数变化 | gain − friction |
| --- | --- | --- | --- | --- |
| 0.30 | 100.00 | 92.50 | −7.50 | −0.40 |
| 0.40 | 100.00 | 100.00 | **0.00** | −0.20 |
| 0.45 | 100.00 | 103.75 | **+3.75** | −0.10 |
| 0.50 | 100.00 | 107.50 | +7.50 | 0.00 |

也就是说存在**两个不同的阈值**：

- **C = 0.40**：`∂index/∂I = 0`，指数停止随投入下降（**颜色**拐点）；
- **C = 0.50**：`gain = friction`（**结构性**收支平衡点，与权重无关）。

当前图把虚线画在 0.5，标注「收益开始超过摩擦」——这句本身没错。但**配色是按 `index` 走的**，颜色真正开始"越投入越亮"是在 0.4，于是在 0.4–0.5 这段里，读者会看到颜色变亮、虚线却告诉他收益还打不过摩擦。图注更进一步写「纵轴低于 0.5 时，投入越多只是把收益变成摩擦」(`MechanismCharts.tsx:193`)，把 `index` 和 `gain/friction` 混为一谈。

**定案：选 A，但 A ≠ 只画两条线。**

只画两条线而不解释，读者会更困惑（"0.40 和 0.50，我该看哪条？"）。B 虽然"不撒谎"，但把问题藏起来而非解决，不符合本文件一贯的"不混口径"原则。A 的正确形态由三件事组成：

1. **两条参考线各自标注自身含义，不做方向性判断**：
   - `C = 0.40 指数拐点` —— 低于此线，投入增加不再提升指数；
   - `C = 0.50 收益 = 摩擦` —— 低于此线，摩擦项大于收益项。
   图注**只陈述两条线各自的含义**，不得出现"该看哪条""以哪条为准"之类的判断。哪个阈值重要取决于读者关心的是"指数"还是"净收益"。
2. **图注删掉混同表述**：「投入越多只是把收益变成摩擦」这类把 `index` 与 `gain/friction` 混为一谈的句子必须删除。
3. **判断交给交互读数**：悬停时**同时**显示 `index`、`gain`、`friction`，让读者自己在两个阈值之间建立理解。这是选 A 成立的前提——若交互做不出来（只剩静态图），A 的收益会打折，此时 B 反而更稳。**阶段 1 的交互式响应面成立，故 A 明显更优。**

**两个阈值必须由权重推导，不得写字面量**：

- `0.40 = frictionWeight / (gainWeight + frictionWeight) = 0.3 / 0.75`——**权重相关**，一次写死，日后调权重会静默失真；
- `0.50` 是 `gain = friction` 的解——结构上恒为 0.5，但仍应从同一份 `gain`/`friction` 定义推导，避免与状态机第 50 行的判定分叉。

当前 `0.45` 与 `0.3` 是 `productivity.ts:34` 内的**内联字面量**，未导出。因此本任务包含一小步模型改动：导出权重（或导出一个 `surfaceThresholds()` 派生函数），并让参考线和图注从它取值。

### 2.4 结尾总结的形式

**结论：表格与星图不是二选一，而是分工。**两者各自解决一件不同的事。

| 方案 | 解决的问题 | 短板 |
| --- | --- | --- |
| 只用表格 | 信息密度、可回查 | 仍是一块静态内容，收束感弱 |
| 只用星图闪耀 | 情绪收束、全局感 | 不承载信息，读者看完仍说不出结论 |
| **表格 + 星图联动** | 两者兼得 | 实现量略大 |

**表格（信息载体）**：6 行，直接对应已有的 `causalNodes`（判断成本 ↓ → AI进入任务 → 要素重组 → 流程重构 → 结果改变 → 新治理），而不是硬凑 8 章——结论章本身不进表，要素章与实验室并入相邻环节更自然。

| 环节 | 被复制的判断 | 留下的约束 | 台账锚点 |
| --- | --- | --- | --- |

- 「被复制的判断」取自 `causalNodes[].proof`（已有文案，不新造）；
- 「留下的约束」取自 `storyBridges[].conclusion`（已有的 7 条小结论）；
- 「台账锚点」**只在有直接对应证据时填数值，否则填「—」**。这是硬约束：上一轮已经确立了"不强行配平"的原则，不允许为了表格好看把不相关的数字塞进去。

**三条收束结论（替换现有两条 blockquote）**：`机制` / `边界` / `选择`。每条不超过两行。

前两条沿用现有文案（`机制`、`边界`，`StorySystem.tsx:143-144`）。**第三条「选择」必须与 `augmentation` 当前阶段绑定**（补强 3），而不是一句泛泛的呼应：

| `stageIndex` | `augmentation` 区间 | 「选择」文案 |
| --- | --- | --- |
| 0 | 0–24 · 任务替代 | 把可复制的判断交给系统，把不可复制的判断留给人 |
| 1 | 25–49 · 局部自动化 | 自动化的边界，取决于谁为错误负责 |
| 2 | 50–74 · 人机协作 | 判断可以分担，责任不能分摊 |
| 3 | 75–100 · 能力扩展 | 新任务出现时，责任边界要重新设计 |

四句共用同一句式，四句全部取自本页已有的语义（任务替代 / 局部自动化 / 人机协作 / 能力扩展，与 `slider-state.ts:35-40` 的阶段名一一对应），不新增内容，只让结尾与用户当下操作真正相连。

**实现约束**：阶段索引必须来自 `resolveSliderState('augmentation', augmentation).stageIndex`，**不得在组件内重新实现分段逻辑**（否则 25 的边界会与滑杆区不一致）。`FinalExpansion` 目前无 props，需要把 `augmentation` 传入。

**星图联动**：`ConclusionNetwork`（`PersistentScene.tsx:232`）已有 8 个节点的放射网络，且已随 `augmentation` 变化点亮比例（`index/(nodes.length-1) <= 0.28 + strength*0.72`）。升级为：

1. 节点与表格的 6 个环节绑定（不是与 8 章一一对应）；
2. 滚动到结论章时**逐节点依次点亮**（stagger）；
3. 表格行 hover / focus → 星图对应节点高亮（**单向**，见 §2.5）；
4. 表格行点击 → `location.hash` 跳回对应章节；
5. 全部点亮后触发一次 `<Sparkles>`。**复用 `PersistentScene.tsx:182` 已有的做法**（`index === selected && <Sparkles count={20} .../>`），不新增依赖。注意 `Scene` 层面本就有一个低透明度常驻 `Sparkles`（`:271`），本次只增加"点亮完成"一次的局部迸发。

保留现有的 `domainPaths` 四标签（研发/制造/医疗/组织）与 `return-to-field` 段落，不推倒重来——它们是上一轮刚验收过的内容。

### 2.5 星图收束的边界

- **高亮是单向的：表格 → 星图**（口子 2）。表格行 hover / focus 时星图对应节点高亮；**星图节点不反向高亮表格**，也不接受指针事件。
  - 理由：表格是**信息载体**，星图是**装饰层**。反向高亮会让装饰层获得操作语义——一旦"点星图会跳转/选中"，星图就悄悄变成了第二个导航，违反本节"星图不承担信息传递"。
  - 验收：星图节点无 `onClick` / `onMouseEnter` / `tabIndex`；`grep` 确认星图侧没有交互事件绑定。
- **减少动效时必须一次全亮**，不能停留在半亮状态，也不能播放 stagger 动画；
- `<Sparkles>` 局部迸发仅在结论章且滚动到位时挂载，避免常驻 3D 负担；
- 星图是"收束感"的装饰层，**必须在任何状态下都不承担信息传递**——即关闭 3D（或 WebGL 不可用）时，表格与三条结论仍然完整成立。

## 3. 分阶段计划

### 阶段 0：尺寸与精度修复（先行，低风险）

#### 任务 0.1：图表基线重构（**口子 1 已核实，必须前置**）

评审提出的验证点已对照源码核实，结论如下：

- **映射函数安全**：阈值图的 `x = (t) => 54 + t * 376`、`y = (r) => 248 - r * 200`（`MechanismCharts.tsx:89-90`）与响应面的 `x`/`y`（由 `surfaceBox` 派生，`:133`、`:153-154`）**都不读取 viewBox**，因此 `threshold.ts` / `productivity.ts` 与既有测试确实零改动。评审"大概率成立"的判断对**这一半**成立。
- **但"只改 viewBox 声明"不成立**：多个**显示坐标写死在旧高度上**，改 viewBox 会直接裁切：

| 图 | 写死坐标 | 依赖的旧高度 | 若 viewBox 缩小 |
| --- | --- | --- | --- |
| 阈值 | x 轴刻度 `y="270"`（`:110`）、轴标题 `y="292"`（`:111`）、交叉线 `y1="48" y2="248"`（`:117`） | 300 | 轴标题 y=292 **超出 270 被裁** |
| 响应面 | x 轴刻度 `y = surfaceBox.bottom + 20` = 272（`:180`）、轴标题 `y="300"`（`:182`）、顶部标题 `y="32"`（`:183`） | 320 | 轴标题 y=300 **超出 280 被裁** |

因此本任务是一个**独立的前置重构**（与上一轮 `ChapterId` 重构同一纪律：先重构、后改缺陷）：

- 为两图各引入一个模块级高度常量（如 `const tradeoffHeight = 300` / `const surfaceHeight = 320`），把 `viewBox` 的高与所有基线（刻度、轴标题、交叉线上下端）都表示成对该常量的偏移；
- **本任务不改变任何视觉输出**：常量取原值 300 / 320，`x()` / `y()` 与所有 `y=` 字面量替换为等价表达式；
- 回归既有测试（`threshold.test.ts`、`productivity.test.ts`），确认仍全绿；
- 完成条件：两图渲染结果与重构前逐像素一致（截图对比），且不存在仍依赖 viewBox 高度的裸字面量。

> 这正是评审口子 1 要求的"若 `x()`/`y()` 引用了 viewBox 常量，必须把常量改为独立参数"。核实的结论是：**映射函数没有引用，但显示坐标引用了**——所以要做的是把显示坐标从 viewBox 高度解耦，让 viewBox 与标签始终保持同步。

## 4. 实施顺序与停止条件

```text
阶段0 基线重构 → 尺寸预算 + 参考线精度
    ↓
阶段1 交互式响应面          ← 到此为止交付「图不再过大 + 可交互」
    ↓
阶段2 结尾总结              ← 到此为止交付「结尾不单薄」
    ↓
阶段3 验收
```

**阶段 0 必须先行，且其中「任务 0.1 基线重构」又先于「任务 0.2 尺寸调整」。**理由有两条：其一，交互热区、准星位置、点击换算全部依赖画布的实际几何，若先在 790px 高的画布上做交互、再回头改尺寸，读数换算与热区都要重做；其二，viewBox 与标签基线必须先解耦，否则缩 viewBox 会静默裁掉轴标签，而这类裁切在常规走查里不容易被发现。

任一阶段未达标时，不通过添加下一阶段内容掩盖问题。
